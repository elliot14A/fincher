## 2. Runtime & Dev Integration Requirements (previously missing)

These are load-bearing, not optional — without them the app either fails to render or fails to reach the API in dev.

1. **Preact/compat aliasing is mandatory.** Every package in the manifest that ends in `-react` (plus `@xyflow/react`) is authored against React's API surface, not Preact's. `vite.config.ts` must alias `react` → `preact/compat`, `react-dom` → `preact/compat`, `react/jsx-runtime` → `preact/jsx-runtime`, and `react-dom/test-utils` → `preact/test-utils`. `preact/compat` ships inside the `preact` package already in the manifest — no extra dependency needed.
   ```ts
   resolve: {
     alias: {
       "react": "preact/compat",
       "react-dom/test-utils": "preact/test-utils",
       "react-dom": "preact/compat",
       "react/jsx-runtime": "preact/jsx-runtime",
     },
   },
   ```
   Not every aliased package is equally safe — some are drop-in, some have known friction, and one has a cleaner native alternative than aliasing at all:

   | Package | Aliasing works? | Notes / alternative |
   |---|---|---|
   | `@tanstack/react-query`, `react-db`, `react-table`, `react-virtual`, `react-form` | ✅ Drop-in | Hooks-only, no DOM-renderer tricks (`useSyncExternalStore`-based); Preact ≥10.5 supports this natively. No alternative needed. |
   | `@tanstack/react-router` | ✅ Works, watch `router-plugin` | Runtime is fine under compat; the Vite codegen plugin (`routeTree.gen.ts`) is framework-agnostic and unaffected. |
   | `@xyflow/react` | ⚠️ Works, but heavier | Drag/resize internals lean on real DOM event quirks and `ResizeObserver`; functionally fine under compat but is the most likely place to hit a rendering edge case — budget time for it in Step 6 (§5). No Preact-native flow-canvas library exists at this quality, so aliasing is the only option. |
   | `sonner` | ✅ Works via compat | Uses `createPortal`, which `preact/compat` supports. No maintained Preact-native toast library exists, so this stays aliased rather than swapped. |
   | `lucide-react` | ⚠️ Works, but skip the alias | Each icon is a trivial `forwardRef` SVG wrapper — works under compat, but **use `lucide-preact` instead** (same icon set, same import names, zero React surface). Swap the manifest dependency: `lucide-preact` not `lucide-react`. This removes one more package from the aliasing surface entirely rather than just tolerating it. |

   Net effect on §1's package manifest: replace `lucide-react` with `lucide-preact`. Everything else in the `-react`/`@xyflow/react` set stays and relies on the alias.
2. **Dev-server API proxy.** `src/lib/api/client.ts` targets `/api` as a relative base so the same code works whether served by `vite dev` or embedded in the Go binary. In dev, `vite.config.ts` needs `server.proxy['/api'] = { target: 'http://localhost:<fincher-port>', changeOrigin: true }`, or requests 404 against Vite's own server.
3. **`src/vite-env.d.ts`** — `/// <reference types="vite/client" />` plus an `ImportMetaEnv` interface, so `import.meta.env.*` (e.g. an SSE base URL override) is typed.
4. **`public/`** — favicon and any static manifest assets, served as-is by Vite and copied into `web/dist` for the Go `embed.FS`.
5. **`openapi-ts.config.ts`** — drives `pnpm generate:api`, producing exactly the three files under `src/lib/api/generated/` (types, SDK functions, Valibot schemas):
   ```ts
   import { defineConfig } from "@hey-api/openapi-ts";

   export default defineConfig({
     input: "../openapi/swagger.json",
     output: "src/lib/api/generated",
     plugins: [
       "@hey-api/client-fetch",
       "@hey-api/typescript",
       "@hey-api/sdk",
       "valibot",
     ],
   });
   ```
   * `@hey-api/client-fetch` — generates a `client` instance the SDK functions call through; `src/lib/api/client.ts` configures it (base URL, headers) and is what the rest of the app imports, not the raw generated client.
   * `@hey-api/typescript` → `types.gen.ts`.
   * `@hey-api/sdk` → `sdk.gen.ts` — one async function per OpenAPI operation, e.g. `getTitles()`, `postDeliveries()`; these are the actual "call the backend" functions every feature's `queryOptions.ts` wraps.
   * `valibot` → `valibot.gen.ts` — runtime schemas per type, for boundary validation.

## 3. Strict Naming Invariants & Structural Rules

1. **Strict camelCase Naming**:
   * All files and folders use **`camelCase`** (e.g. `calendarGrid.tsx`, `calendarGrid.css.ts`, `queryKeys.ts`, `queryOptions.ts`, `holdOverrideModal.tsx`).
   * No kebab-case (`calendar-grid.tsx` ❌) and no PascalCase files (`CalendarGrid.tsx` ❌).
2. **Deep Component Co-location**:
   * UI components and feature sub-components **never** sit dumped in a flat directory.
   * Every component lives inside its own dedicated directory alongside its styling and helper files:
     * `src/components/ui/button/button.tsx` + `src/components/ui/button/button.css.ts` + `src/components/ui/button/index.ts`
     * `src/features/calendar/grid/calendarGrid.tsx` + `src/features/calendar/grid/calendarGrid.css.ts` + `src/features/calendar/grid/index.ts`
   * The same rule applies to hooks — a feature-local hook is never loose at the feature root; it lives in that feature's own `hooks/` subdir (e.g. `src/features/lineage/hooks/useLineageLayout.ts`). Only hooks shared across *multiple* features live outside `features/`, under `src/lib/hooks/`.
   * **Every directory gets an `index.ts` barrel** — this applies to *any* subdirectory (component dirs, `hooks/`, etc.), not just UI components: it's the one importable surface for everything inside it. It does **not** apply to standalone files sitting directly at a feature's root (`queryKeys.ts`, `queryOptions.ts`) — those aren't directories, and are re-exported through the feature's own top-level `index.ts` instead.
3. **Query Key & Option Separation**:
   * Every feature has dedicated `queryKeys.ts` (deterministic key factory) and `queryOptions.ts` (TanStack Query options using generated Hey API SDK).
4. **Zero Runtime Styling**:
   * All styles are written in `*.css.ts` using `@vanilla-extract/css` and `@vanilla-extract/recipes` consuming type-safe tokens from `src/styles/theme.css.ts`.
5. **Framework-mandated exception to the camelCase rule**:
   * TanStack Router's file-based routing conventions (`$id.tsx`, `__root.tsx`, `index.tsx`) are dictated by the router, not a naming choice, and are exempt from Rule 1. They are confined to `src/routes/`; every file under `src/features/`, `src/components/`, `src/lib/`, `src/db/`, `src/styles/` still follows strict camelCase with no exceptions — except `src/lib/api/generated/` (§2, untouched Hey API output, not hand-authored).

## 5. Execution Milestones

* **Step 1: Scaffolding & Configuration**:
  * Setup `web/` with `bun`, `vite.config.ts` (Preact preset, Vanilla Extract, TanStack Router plugin), `tsconfig.json`, `biome.json`, and `openapi-ts.config.ts`.
* **Step 2: Design Tokens & Base Theme**:
  * Build `src/styles/theme.css.ts` with dark operations theme variables and `src/app.css.ts`.
* **Step 3: Auto-Generated SDK**:
  * Run `bun run generate:api` against `openapi/swagger.json` producing `src/api/generated/`.
* **Step 4: Shared UI Primitives**:
  * Implement co-located `button`, `badge`, `modal`, `dataTable`, `input`, `drawer` using `@vanilla-extract/recipes`.
* **Step 5: Shell & Routing**:
  * Implement `src/features/layout/` and `src/routes/__root.tsx` with topbar and sidebar navigation.
* **Step 6: Core Features**:
  * Implement `calendar`, `lineage` (XYFlow DAG), `deliveries` (virtualized table), `vendors`, and `runs` (live SSE inspector).
* **Step 7: Backend Embed & Verification**:
  * Wire `web/dist` embedding in Go server and run full verification suite.
