### Finding 1 [Critical] — The committed/served OpenAPI spec is empty; the whole feature is non-functional as shipped

```
$ cat openapi/swagger.json
{
    "produces": ["application/json"],
    "swagger": "2.0",
    "info": {...},
    "basePath": "/api",
    "paths": {}
}
```
`paths: {}` and no `definitions` at all — despite 28 fully-annotated handlers across `internal/api/**`. `/openapi.json` and `/openapi.yaml` serve exactly this empty document at runtime (confirmed via `openapi/spec.go`'s `//go:embed` wiring, and the files it embeds).

**Root cause**: `openapi/generate.go`'s `//go:generate` directive is
```go
//go:generate go run github.com/swaggo/swag/cmd/swag@latest init -g ../cmd/fincher/main.go -o . --outputTypes yaml,json
```
`go:generate` runs with the working directory set to the file's own directory (`openapi/`). `swag init`'s search dir (`-d`) defaults to `./` when not passed — so this command parses only `openapi/` itself (which contains no `@Router` annotations) for handler comments; `-g ../cmd/fincher/main.go` only tells it where to find the *general* info block, it does not extend the search dir. Since none of `internal/api/**`'s annotated files are ever visited, `swag` emits a spec with only the top-level `info`/`basePath` and zero paths/definitions.

I reproduced this and confirmed the fix — running from the repo root with a search dir that covers `internal/api/**` and `--parseInternal` (needed because the handler/model packages are non-exported internal packages) produces a populated spec:
```
$ go run github.com/swaggo/swag/cmd/swag@latest init \
    -g cmd/fincher/main.go -d . --outputTypes yaml,json -o ./openapi \
    --parseInternal --parseDepth 5
...
paths: 13
definitions: 20
```
(13 path templates because swag groups `{id}` variants per route; 20 definitions cover all six entities' domain models plus their `Update*Input` variants and `errors.DomainError`.)

**Impact**: any consumer of `/openapi.json`/`/openapi.yaml` — API client codegen, a docs UI, contract testing — gets a spec that looks well-formed (valid JSON/YAML, correct `info`/`basePath`) but describes zero endpoints. This would likely pass a casual smoke test (`curl /openapi.json` returns `200` with valid JSON) while being completely useless, which is exactly the kind of failure that's easy to miss without actually inspecting the payload — as apparently happened here.

**Fix direction**: change the `go:generate` directive to run with a search dir covering the actual annotated packages and `--parseInternal` set, e.g.:
```go
//go:generate go run github.com/swaggo/swag/cmd/swag@latest init -g cmd/fincher/main.go -d ../ --outputTypes yaml,json -o . --parseInternal --parseDepth 5
```
(note `-g` also needs to drop the `../` prefix or `-d` needs to be `../` consistently — verify path resolution once fixed) then regenerate and commit the real `swagger.yaml`/`swagger.json`. Add a one-line CI/test check that fails if `openapi/swagger.json`'s `paths` is empty, so this class of silent breakage can't recur undetected.

### Finding 2 [Low] — `go.mod`/`go.sum` pulled in a large, partially-unused dependency surface for a feature that isn't wired up correctly yet

`go.mod` gained `github.com/ogen-go/ogen`, `github.com/go-faster/errors`, `github.com/go-faster/jx`, `go.opentelemetry.io/otel{,/metric,/trace}` as direct requires, plus ~25 new indirect deps (`swaggo/swag`, `swaggo/echo-swagger`, `swaggo/files/v2`, `go-openapi/*`, `urfave/cli/v2`, `go.uber.org/zap`, etc.). A grep across `internal/`, `cmd/`, `openapi/` shows no actual import of `ogen`, `go-faster/*`, or the OpenTelemetry packages anywhere in the tree — only `swaggo/swag`'s CLI (invoked via `go run .../swag/cmd/swag@latest` in `generate.go`, itself unaffected by whether it's a direct or tool dependency) and the embedded static files are actually used. `ogen`/OTel look like they were added by `go mod tidy` picking up something transitive from the swag toolchain's own module graph rather than being genuinely needed by this codebase, given nothing imports them directly.

**Fix direction**: run `go mod tidy` after fixing Finding 1 and re-verify — some of these may drop out once the generator is invoked correctly and dependencies settle; if `ogen`/OTel remain listed as *direct* requires with nothing importing them, move them or drop them (a `tools.go` blank-import pattern for the swag CLI would also make its dependency explicit and pinned, rather than relying on `@latest` in the `go:generate` line, which is its own minor reproducibility concern — an unpinned version means `go generate` output can silently change between runs on different days).

### Finding 3 [Low] — `//go:generate ... swag@latest` is unpinned

Beyond the dependency-surface concern above, `@latest` means every future `go generate ./openapi` run could pull a different `swag` version with different output formatting or behavior, with no way to reproduce a prior spec deterministically. Low severity since the spec is currently checked in (so this doesn't block builds), but worth pinning once Finding 1 is fixed and the generator is actually exercised regularly.

**Fix direction**: pin to a specific tagged version (e.g. `swag@v1.16.2`, matching the version already resolved in `go.sum`) instead of `@latest`.
